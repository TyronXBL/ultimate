Run a conversation on the next backup model of its agent definition when its model answers with a rate limit, a capacity or a quota error, and put its primary back at a run that starts 30 minutes later.

## How it works

- A definition orders its backup models with `fallback` (`provider/modelId[:thinking]`, see `docs/subagents.md`); an overlay replaces the list. A conversation without one never switches. It switches only when the answer that failed is a limit (`limited()` in `lib/rate-limit.ts`) — a rate limit (429, "too many requests", `rate_limit_exceeded`), a provider at capacity (529, "overloaded", "at capacity", `server_busy`, `ResourceExhausted`) or an exhausted account (`insufficient_quota`, "quota exceeded", `usage_limit`, "out of budget", "billing", `credits_required`). An auth failure, a network error and a context overflow end the run as before.
- The extension watches commits for assistant error entries. In the commit that records the first limited one it uses `ModelsApi.setModel` to record the owner and move the model to the first backup of the definition that has a login here, room for the conversation and was not tried in this switch, clamping the backup's own or primary's thinking level. Room means its context window holds the conversation's context (`ContextUsageDoc`, measured by the last answer that reported usage: a limit's error reports none) plus 32k: a smaller backup would start a blocking compaction at once, whose summary the limit may leave no model to write (#189897 switched at 270k to a 272k window, #191380 to a 128k one, #207552 to a 128k one when the size read 0 after a 429). Pi's retry of the failed response (2 s later, up to three times) then runs on the backup. A preview's model (`previewModel()`) never switches.
- The backup record lives in `models.owner` as `by: 'backup'`, alongside its primary, thinking, current backup, switch time, tried models, the limit, and the original owner underneath. `backupStep` remains the pure decision helper, using a backup view derived from the owner. The old `backup.state` document is read only to migrate records from hosts that predate owner-based backups; the migration can go once no host has an old record. A subagent's row and card show the backup from `models.backups`, which `setModel` keeps beside the owner, so a pick or a return drops it in the same write. The switch leaves one `backup.switch` card in that conversation: the model that failed, the backup it runs on now, which limit, and the error. @ultimate gets one `backup.notice` line naming the conversation and the switch, which opens it.
- A second limit on the backup, or on the backup's backup, switches on, one card per failure: `primary` and `thinking` stay the ones the conversation came from and `tried` lists the models it left, so each backup is taken once per switch. A definition with no fallback leaves the failure as it was and Pi retries the same model.

## Models out of quota

A quota answer (`limitOf` is `quota`: an exhausted subscription, an out-of-credit 402) records its model in `backup.exhausted` on the root, machine-wide, until the reset its provider reports (`Resets`, read after the error); when it reports none the account is out of credit, which no time resets (#207552: GLM's 402 counted for an hour and was tried again each night). Every conversation then skips it, for a switch and for a summary ("quota until …" or "out of credit" on the wait card), instead of trying it once each (#191380, #191455 and #194520 all tried the same two). It is per model, not per provider: one model's weekly limit leaves the provider's other models alone. An entry ends when its time passes, when that model answers anything that is no error (a pick of it after a top-up, a primary it was), or when its provider's login changes (`LoginChanged`), so logging in again clears it. `exhaustedStep` in `state.ts` is its only writer. A wait for a primary that is out of quota lasts until that reset; a reset more than 24 hours away, or none, starts no wait.

## Waiting for the primary

When a definition has backups but none can take the limit (each tried, without a login, or too small), the conversation goes back to its primary at its thinking level and waits: `models.owner` becomes `by: 'limit-wait'` with the primary, when the wait began (`since`), the next try (`until`), which wait in a row it is (`attempt`), the models it left and the limit, over the owner it replaced. `backupStep` decides it (`waiting`, `held`, `gave-up`, `resumed` in `state.ts`), `setModel` stores it.

- The next try is 1, 2, 4, 8, 16, then every 30 minutes after the wait's latest try; a quota of the primary whose provider reports when it resets (`Resets`) waits until then. Each conversation adds its own share of a spread (`jitterOf`: up to a quarter of the backoff, or a minute after a reset), so conversations waiting on one account do not all try it in the same second.
- A wait never outlasts 24 hours from its start: a reset reported further away starts none, and the try that would pass it gives up, so the failure is reported as before.
- The run ends as Pi ends it. The watchdog (`extensions/watchdog`) continues it at `until`, @ultimate's own run included: each try with one input asking it to continue; @ultimate's later tries of the same wait, and the runs of a try's backups, with a `continue` submission that adds no message, so its long wait leaves one in the context (Pi leaves the failed answers out of it). A subagent's report and a branch's final answer reach their parent or starter only as the answer to an input, so they get one per try. Each try still makes Pi's own quick retries of a rate limit, since Pi's retry policy is harness-wide; inputs that arrive meanwhile run on the primary, and a limit there before `until` changes nothing (`held`), so it never pauses the host. Their failures sleep until the same `until` and one continuation answers them all, with every input in its context.
- A try asks the primary, then the backups again: one on another account may have room long before the primary. A backup it moves to keeps the wait in its record (`wait`: its `since` and `attempt`), without a `backup.switch` card or notice, so a limit there with no backup left goes on with the same wait at the next attempt (#251493: each try's backup began the wait again at attempt 1, so tries came every 64 s all night, each with a wait card and two notices to @ultimate). A try costs one request per model that can take the conversation (backups out of quota, out of credit or too small are skipped), and Pi's quick retries left in that run go to the primary and are `held`.
- Only an answer ends the wait: the primary's (`return`, back to the owner under it), or a try's backup's, which keeps the conversation on that backup without the wait, back to its primary after the cooldown like any switch; or a pick, or the 24 hours.
- A pick or a creator's `start` replaces the owner, which ends the wait; the watchdog then continues nothing.
- The conversation gets one `backup.wait` card where the wait began: the model that failed, the primary, each backup skipped and why, the error, and live from `models.owner` the next try and which one it is, or "wait over". It is display-only, so it shows at once also while the run is still busy; one with a model line would wait for the run to end, and a failed run keeps it queued until the wait's continuation (#207552). While a try asks a backup the footer says which. @ultimate gets one `backup.notice` line with `until` when the wait starts, and one with `resumed` when an answer ends it; a wait that gives up is reported by the watchdog's failure card.
- After `COOLDOWN_MINUTES` (30) it goes back: at the start of the next run (`beforeInput`), the conversation returns to `primary` with `thinking` as it was, and one `backup.return` divider marks it ("back on x after 30 minutes on the backup y"). A run that starts sooner stays on the backup; a primary without a login here yet keeps the backup, and the next run looks again.
- A pick, `models.fallback` or a creator's `start` (a subagent child, a standing agent's pin, a branch given a model) replaces the owner, even when the user picks the exact backup model, so a later cooldown cannot undo that choice. Every model writer goes through the owner, so a conversation on a backup runs on its backup. A fork made while on a backup inherits its owner record and returns to the same primary after cooldown; a standing agent's refresh keeps a backup it runs on.
- Built-in `pause` hands it the same rate limit first: a conversation whose definition has a backup model for it goes on there, and the hold it took is released again, so a rate limit it can leave never pauses the host. Without one the host pauses as before, and Play continues the held run through Pi's retry on the backup the extension set meanwhile; the switch back happens 30 minutes after the switch, not after Play. A limit Pi does not retry (a quota or usage limit, or a rate limit past its retries) ends the run: `watchdog` waits 5 seconds, sees the new model in `AgentDoc`, and continues the conversation on it instead of reporting the failure.

## API

`BackupApi.fallBack(conversationId, message, entryId)` (`api.ts`) makes the same switch for a failure another extension sees first: `pause` asks it before pausing for a rate limit, and returns whether the conversation runs on a backup because of it. It is one at a time across reloads and once per failed entry, so the failure reaching it twice leaves one card.

It also fills the `models.backup-order` extension point (`BackupOrder` in `extensions/models/api.ts`): the models a conversation would move to, in order, were its model and each after it limited (`backupOrder` in `state.ts`, built from `backupStep`): the definition's untried backups with a login, room for the conversation and quota left, then the primary once its cooldown has passed. It switches nothing; lineage's compaction summary goes through it when the conversation's model is limited. When no model could write the summary, lineage hands it the refusals (`refused`, its own model first): the own model's limit decides as its answer would, the backups that refused count as tried ("rate limit on the summary") and a quota among them as exhausted, so the conversation waits on its primary before the compaction fails its run, and the watchdog continues it (#207552: the summary's failure ended three runs for the night).
